Задача: реализовать кризисы компаний. Сейчас есть только таблица company_crises, рантайм-логики нет. Следуй инвариантам из EXCHANGE_2_RULES.md (сохранение монет, целочисленная математика, атомарные батчи, идемпотентность).

Схема. Миграция (идемпотентная) к company_crises: добавить `options_json TEXT`, `timeout_json TEXT`, `resolved_option TEXT`, `resolved_at INTEGER`. Статусы: 'pending' -> 'resolved' | 'expired'. Уникальный message_id уже есть — учти это (он заполняется после отправки сообщения).

1. Каталог (collector/src/crisisCatalog.ts). Виды: налоговая проверка, конкуренты, утечка данных, скандал, судебный иск, удачная возможность. На каждый вид минимум 3 сценария (scenario_text на русском, живо и коротко, без реальных людей и брендов). У сценария 2–3 варианта действий владельца:
   { id, label, emoji, outcomes: [{ weight, pct_bps, text }] }
   pct_bps — изменение казны в bps от текущей казны (отрицательное = потеря). Внутри варианта сумма weight = 100. Вариант может быть безопасным (один исход) или рискованным (несколько).
   timeout_json — исход, если владелец не ответил за CRISIS_TTL_HOURS.
   Ограничения каталога: |потеря| <= CRISIS_MAX_LOSS_BPS, прибыль <= CRISIS_MAX_GAIN_BPS; ожидаемые значения (EV) вариантов одного сценария отличаются не более чем на 3 п.п. (чтобы был реальный выбор между надёжным и рискованным); EV исхода по таймауту СТРОГО хуже EV любого варианта. Напиши unit-тест, который проверяет все эти правила для всего каталога.

2. Спавн (collector/src/crises.ts). Задача с таймером раз в 30 минут. Для каждой гильдии, если now >= exchange_guild_state.next_crisis_at (или NULL):
   - кандидаты: компания не frozen, treasury >= CRISIS_MIN_TREASURY, circulating > 0, нет pending-кризиса, последний кризис компании закончился более CRISIS_COMPANY_COOLDOWN_HOURS назад;
   - выбор случайный, вес = 1 + число различных внешних (не владелец) держателей;
   - нет кандидатов -> просто сдвинуть next_crisis_at;
   - в ОДНОМ батче: INSERT company_crises (status='pending', expires_at = now + CRISIS_TTL_HOURS, scenario_text, options_json, timeout_json), событие 'crisis_spawn' в market_events, обновление next_crisis_at на случайное время через CRISIS_MIN..MAX часов. Условный UPDATE next_crisis_at защищает от двойного спавна при параллельных запусках.
   - отправитель market_events для 'crisis_spawn' публикует embed (тикер, сценарий, обратный отсчёт через <t:UNIX:R>) с кнопками вариантов, custom_id = `crisis:<id>:<optionId>`, упоминание владельца только через allowed_mentions.users, и записывает channel_id/message_id обратно в company_crises.

3. Разрешение (worker: обработчик кнопок, подключи в worker.ts тем же способом, каким уже маршрутизируются компоненты; изучи существующий паттерн). Нажатие:
   - нажать может только владелец компании, остальным ephemeral-ответ «Решает только владелец компании»;
   - если кризис уже не pending / истёк / удалён (например, после ликвидации сезона), ответь ephemeral «Кризис уже закрыт»;
   - исход выбирается на сервере взвешенным случайным выбором;
   - delta = trunc(treasury * pct_bps / 10000). Потеря ограничена так, чтобы казна осталась >= 1. Прибыль ограничена min(CRISIS_MAX_GAIN_COINS, баланс server_reserve). Все деньги идут через резерв: потеря +резерв, прибыль -резерв (инвариант сохранения монет);
   - ОДИН db.batch с guard: (1) UPDATE company_crises SET status='resolved', resolved_option, resolved_at, outcome_text, treasury_delta WHERE id=? AND status='pending' AND expires_at > now; (2) UPDATE companies SET treasury = treasury + delta, mood_bps/mood_updated_at (см. ниже) — только если (1) сработал; (3) UPDATE server_reserve зеркально; (4) INSERT company_nav_history reason='crisis'; (5) событие 'crisis_resolved'. Если состояние казны изменилось между расчётом и батчем (параллельная сделка), пересчитай и повтори до 3 раз;
   - настроение: mood = applyMoodShift(effectiveMood, +pct_bps) для прибыли, а для потери -(|pct_bps| * CRISIS_LOSS_MOOD_FACTOR) (целочисленно), с обрезкой в диапазон;
   - ответ на нажатие — обновление исходного сообщения (тип ответа UPDATE_MESSAGE): убери кнопки, покажи исход и изменение казны/NAV.

4. Таймаут (collector, раз в минуту): все pending с expires_at <= now применяют timeout_json теми же правилами и тем же атомарным батчем, статус 'expired'; исходное сообщение редактируется через REST (кнопки убираются), публикуется событие 'crisis_resolved'. Задача идемпотентна.

5. Ограничения Discord: custom_id <= 100 символов, label <= 80, поля embed в лимитах. Ошибки отправки не должны откатывать уже применённый исход.

Критерий готовности: кризис спавнится в тестовой гильдии (для теста временно поставь маленькие интервалы через константы или переменные окружения), кнопки работают только для владельца, повторное нажатие безопасно, таймаут применяет худший исход, сумма монет в системе сохраняется (добавь тест на чистую функцию расчёта дельты и на каталог), после ликвидации сезона кнопки старых кризисов отвечают «Кризис уже закрыт».
