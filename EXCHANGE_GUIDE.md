## 1. Архитектура и основы биржи

### 1.1. Таблицы БД

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `companies` | Компания-эмитент | `guild_id`, `owner_id`, `name`, `ticker`, `description`, `treasury`, `total_shares = 100`, `available_shares`, `last_growth_day`, `frozen`, `created_at` |
| `company_shares` | Пакеты акций игроков | PK `(user_id, company_id)`, `shares_count` |
| `server_reserve` | Общий банк сервера | PK `guild_id`, `balance` |
| `company_crises` | Кризисы компаний | `company_id`, `kind`, `scenario_text`, `player_reply`, `outcome_text`, `treasury_delta`, `status`, `expires_at` |

Ограничения уникальности `companies`: `UNIQUE(guild_id, ticker)` и `UNIQUE(guild_id, owner_id)`.

**Доступ к БД:** обработчики биржи (`company.ts`, `invest.ts`, `stocks.ts`) создают собственный клиент `createClient` и работают с таблицами напрямую. Общий слой `worker/src/db/queries.ts` хелперов для биржи **не содержит** — там только пользователи, монеты, дуэли, инвентарь, рынок и квесты (проверено).

### 1.2. Компания, казна, акции

- **Компания** — эмитент ровно **100 акций** (`total_shares = 100`), жёстко привязана к гильдии.
- **Казна (`treasury`)** — внутренний счёт компании в монетах 🪙. Стартует с **500 🪙**. Казна не принадлежит никому лично: торговые операции её прокачивают, а в конце сезона она распределяется держателям акций (дивиденды).
- **Акции в обращении (`circulating`)** — сколько акций сейчас на руках у игроков:

  ```
  circulating = 100 − available_shares
  ```

- **Свободный флоат (`available_shares`)** — акции, «лежащие на бирже» и доступные к покупке. Стартует с **49**.
- **Заморозка (`frozen`)** — флаг приостановки торгов: блокирует и покупку, и продажу.

### 1.3. Резерв сервера (`server_reserve`)

Общий «котёл» сервера — одна строка на гильдию. Роль:

- **Наполняется** комиссиями трейдеров и «излишком» при создании компаний (§5.2);
- **Расходуется** на суточный рост казны компаний (§5);
- **НЕ обнуляется** при ликвидации сезона — баланс переходит в новый сезон.

### 1.4. Распределение акций при создании

| Пакет | Акций | Кому |
|---|---|---|
| Контрольный пакет | **51** | Основателю (начисляется мгновенно при создании) |
| Свободная продажа | **49** | Остаётся в `available_shares` (открытый рынок) |
| **Всего** | **100** | |

### 1.5. Модель ценообразования: «открытый фонд по NAV»

Цена одной акции = доля казны на акцию:

```
NAV = treasury / circulating,   circulating = 100 − available_shares
```

Ключевое свойство (следует из формул §3): покупка и продажа проходят **по текущему NAV** (средняя цена, а не маржинальная), поэтому сама сделка цену практически не двигает. Точная математика:

- Покупка `k` акций: казна растёт на `ceil(k·T/C)`, circulating растёт на `k` → `NAV' = (T + ceil(kT/C)) / (C + k) ≥ NAV`;
- Продажа `k` акций: казна уменьшается на `floor(kT/C)`, circulating уменьшается на `k` → `NAV' = (T − floor(kT/C)) / (C − k) ≥ NAV`.

То есть **любая сделка не снижает NAV** (округления ceil/floor всегда в пользу казны), а заметный рост/падение котировки дают только **внешние** потоки: суточный рост казны (+, §5) и кризисы (±, §6). Это модель «открытого фонда»: компания эмитирует/выкупает акции по справедливой стоимости доли.

### 1.6. Контур сохранения монет (без инфляции)

Экономика замкнута — монеты не создаются и не сжигаются, все операции сходятся копейка в копейку:

| Операция | Поток монет |
|---|---|
| Создание компании | Взнос игрока → 500 в казну компании + (взнос − 500) в резерв |
| Покупка акций | Покупатель → казна (база) + основатель (3% базы) + резерв (остаток) |
| Продажа акций | Казна → продавец (95%) + резерв (5%) |
| Суточный рост | Резерв → казна компании |
| Ликвидация сезона | Казна → держатели акций + остаток → резерв |

### 1.7. Жизненный цикл компании

```
/company-create ─► торговля (/invest, /divest) ─► суточный рост (1 раз/сутки)
      ─► кризисы (± казна) ─► смена сезона ─► ликвидация (дивиденды) ─► удаление
```

## 2. Создание компании — `/company-create`

### 2.1. Аргументы и валидация

| Аргумент | Обязателен | Правила |
|---|---|---|
| `name` | да | После очистки от спецсимволов: **3–32 символа** |
| `ticker` | нет | `^[A-Z]{2,5}$` — 2–5 заглавных латинских букв |
| `description` | да* | Очистка + обрезка до **200 символов** (\* в регистрации collector — `required: true`; обработчик допускает отсутствие) |

Очистка (`sanitizeText`): из текста удаляются символы `@ < > \` * _ ~ | [ ] ( #`, переводы строк (`\r\n`) и табуляции.

Порядок проверок в обработчике: имя → тикер → описание → уникальности → расчёт цены → списание.

### 2.2. Автогенерация тикера

Если тикер не передан или пуст:

1. Из названия берутся **все латинские буквы**, склеиваются, приводятся к верхнему регистру, берутся первые **4**;
2. Если латинских букв меньше 2 (например, кириллическое название) — тикер **`CORP`**.

Примеры: `"Vlad Stroy"` → `VLAD`; `"Ромашка"` → `CORP`; `"GooglePlex"` → `GOOG`.

### 2.3. Уникальность и лимиты

- **На игрока**: не более **одной** основанной компании на гильдию (`UNIQUE(guild_id, owner_id)` + явная проверка «У вас уже есть основанная компания на этом сервере»);
- **Тикер** уникален в гильдии (`UNIQUE(guild_id, ticker)`);
- **Название** уникально в гильдии **без учёта регистра** (сравнение в JS через `toLowerCase`);
- **На сервер**: жёсткого лимита числа компаний нет — ограничителем выступает растущая цена (§2.4).

### 2.4. Стоимость создания

```
count = число компаний на сервере (до создания)
cost  = 1000,                   если count = 0
cost  = 1000 + count × 30000,   иначе
```

| Компания на сервере | Цена |
|---|---|
| 1-я | 1 000 🪙 |
| 2-я | 31 000 🪙 |
| 3-я | 61 000 🪙 |
| 10-я | 271 000 🪙 |

### 2.5. Куда уходит взнос

```
взнос = 500 (стартовая казна компании) + (взнос − 500) (в server_reserve)
```

Примеры: 1-я компания → 500 в казну + 500 в резерв; 2-я → 500 в казну + 30 500 в резерв. Ничего не сжигается.

### 2.6. Что создаётся и гарантии атомарности

- `companies`: `treasury = 500`, `total_shares = 100`, `available_shares = 49`, `frozen = 0`, `last_growth_day = NULL` (новая компания может получить рост в первый же тик);
- `company_shares`: основателю **51 акция**;
- Списание монет атомарное: `UPDATE users SET coins = coins - ? WHERE ... AND coins >= ?` — при нехватке баланса отказ;
- Всё выполняется в **интерактивной транзакции** (`db.transaction("write")`) с `commit`/`rollback`; сообщение об успехе отправляется **строго после** завершения транзакции (после `finally`).

## 3. Математика котировок (ценообразование)

### 3.1. Базовая цена (NAV)

```
circulating = 100 − available_shares
NAV         = treasury / circulating
```

В `/stocks` NAV отображается с отбрасыванием (floor) до 2 знаков:

```
nav = floor(treasury × 100 / circulating) / 100
```

### 3.2. Покупка — `/invest` (точные формулы из кода)

```
baseCost   = floor((amount × treasury + circulating − 1) / circulating)   // = ceil(amount × treasury / circulating)
totalCost  = floor((baseCost × 106 + 99) / 100)                           // = ceil(baseCost × 1.06)
founderFee = floor(baseCost × 3 / 100)                                    // 3% роялти основателю
reserveFee = totalCost − baseCost − founderFee                            // остаток (~3% + округление) в резерв
```

Предварительные проверки: компания существует; `frozen = 0`; `available_shares ≥ amount`; `treasury ≥ 1` и `circulating > 0` (иначе «Компания банкрот»); у покупателя хватает `totalCost`.

Эффект: покупатель `−totalCost`; казна `+baseCost`; `available_shares −amount`; основатель `+founderFee` (если записи основателя нет в `users` — роялти уходит в резерв); резерв `+reserveFee`; акции покупателю (upsert по `(user_id, company_id)`).

### 3.3. Продажа — `/divest` (точные формулы из кода)

```
basePayout = floor(amount × treasury / circulating)    // 0, если circulating ≤ 0
netPayout  = floor(basePayout × 95 / 100)              // 95% продавцу
reserveCut = basePayout − netPayout                    // 5% в резерв
```

Предварительные проверки: компания существует; `frozen = 0`; у продавца есть `amount` акций; `basePayout ≥ 1`; казна покрывает выкуп (`treasury ≥ basePayout`); правило контрольного пакета (§4.3).

Эффект: продавец `+netPayout`; казна `−basePayout`; `available_shares +amount`; резерв `+reserveCut`; пустые записи акций (`shares_count ≤ 0`) удаляются.

### 3.4. Комиссии, спред, проскальзывание

- **Комиссия на покупке: +6%** к базовой стоимости (3% — роялти основателю, ~3% + остаток округления — в резерв);
- **Комиссия на продаже: −5%** (в резерв сервера);
- **Спред**: покупка по `1.06 × NAV`, продажа по `0.95 × NAV` → круговая сделка «купил → продал» теряет ≈ **10–11%**;
- **Проскальзывания внутри сделки нет** — весь объём идёт по текущему NAV (средняя цена, а не маржинальная). Округления в пользу системы: покупка — `ceil`, продажа — `floor`;
- **Движение цены**: сделка по NAV нейтральна (§1.5) и даже слабо поднимает NAV за счёт округлений; заметно цену двигают только суточный рост (+) и кризисы (±).

### 3.5. Сквозной пример на реальных числах

Компания **«ВладСтрой» (VLAD)**: `treasury = 5000`, `available_shares = 40` → `circulating = 60`, `NAV = 5000/60 = 83.33 🪙`.

**Покупка 5 акций:**

- `baseCost = ceil(5 × 5000 / 60) = ceil(416.67) = 417`
- `totalCost = ceil(417 × 1.06) = ceil(442.02) = 443`
- `founderFee = floor(417 × 0.03) = 12`
- `reserveFee = 443 − 417 − 12 = 14`

Итог: покупатель −443 🪙; казна 5000 → **5417**; `available_shares` 40 → **35** (circulating 65); основатель +12; резерв +14. Новый NAV = 5417/65 = **83.33** — сделка цену не сдвинула (нейтральность по NAV).

**Продажа тех же 5 акций:**

- `basePayout = floor(5 × 5417 / 65) = floor(416.69) = 416`
- `netPayout = floor(416 × 0.95) = 395`
- `reserveCut = 416 − 395 = 21`

Итог: продавец +395 🪙; казна 5417 → **5001**; `available_shares` 35 → **40** (circulating 60); резерв +21. Новый NAV = 5001/60 = **83.35** (микророст за счёт округлений).

**Круговая сделка**: заплатил 443, получил 395 → убыток 48 🪙 (≈10.8%) — это цена ликвидности плюс комиссии.

## 4. Механика торговли

### 4.1. Куда уходят монеты при покупке

Ничего не сжигается. `totalCost` покупателя раскладывается на три части:

- `baseCost` → **в казну компании** (растит NAV для будущих продавцов);
- `founderFee` (3% базы) → **основателю** как роялти;
- `reserveFee` (остаток) → **в резерв сервера**.

### 4.2. Откуда берутся монеты при продаже

Из **казны компании**: компания выкупает акции у игрока на `basePayout`, из которых продавец получает `netPayout` (95%), а `reserveCut` (5%) уходит в резерв. Если казны не хватает (`treasury < basePayout`) — сделка отклоняется («Недостаточно средств в казне»). Казна, таким образом, — подушка, гарантирующая выкуп акций; её наполняют покупатели и суточный рост.

### 4.3. Правило контрольного пакета (51 акция)

**Заявленное правило** (комментарий в коде и текст ошибки): владелец не может размыть свой контрольный пакет — после продажи у него должно оставаться **минимум 51 акция**.

**Фактическая реализация** — условие прямо в `UPDATE` (атомарно, без гонок между параллельными `/divest`):

```sql
UPDATE company_shares
SET shares_count = shares_count - ?
WHERE user_id = ? AND company_id = ? AND shares_count >= ?
  AND (shares_count - ? >= 51 OR ? = 0)
-- 6-й параметр: isOwner ? 0 : 1
```

Разбор фактического поведения:

- **Владелец** (параметр `0`): подусловие `0 = 0` → TRUE → ограничение **обходится** → владелец может продать все акции вплоть до 0;
- **Не-владелец** (параметр `1`): подусловие `1 = 0` → FALSE → действует ограничение «останется ≥ 51» — то есть обычный инвестор, набравший 51+ акций, не сможет продаться ниже 51.

> ⚠️ **Расхождение кода с комментарием**: логика инвертирована относительно задокументированного замысла («контрольный пакет владельца защищён»). Судя по комментарию и тексту ошибки, ограничение должно было действовать для владельца (для этого 6-й параметр должен быть `isOwner ? 1 : 0` либо сравнение `? = 1`). В текущем виде фактическая защита стоит на не-владельцах с крупным пакетом. Подробнее — Приложение Б.

Позитив: проверка и списание выполняются **одним атомарным UPDATE** — гонки между параллельными `/divest` исключены; после списания пустые записи удаляются.

### 4.4. Прочие ограничения торговли

- `amount` — строго целое число ≥ 1;
- `frozen = 1` блокирует и покупку, и продажу («Компания заморожена — торги приостановлены»);
- Покупка в банкротную компанию запрещена (`treasury < 1` или `circulating ≤ 0`);
- Продажа с выкупом 0 монет запрещена (`basePayout < 1`);
- Нельзя купить больше, чем есть в свободной продаже (`available_shares`).

## 5. Суточный рост и пассивный доход

### 5.1. `processDailyCompanyGrowth` — как работает

- **Расписание**: тикер в collector каждые **10 минут** (+ запуск при старте);
- **Идемпотентность**: компания обрабатывается не чаще раза в сутки — по маркеру `last_growth_day` (дата по Владивостоку, `YYYY-MM-DD`); условие `last_growth_day IS NULL OR last_growth_day < today`;
- **Порядок**: гильдии с компаниями; внутри гильдии компании, готовые к росту, в **случайном порядке** (`ORDER BY RANDOM()`) — честно при дефиците резерва;
- **Формула гранта**:

  ```
  desired = min(floor(treasury × 0.01), 100)      // 1% казны, но не более 100 🪙
  grant   = min(desired, balance(server_reserve)) // не больше, чем есть в резерве
  ```

- **Если `grant > 0`** — атомарный `db.batch` из двух условных `UPDATE`:
  1. `companies`: `treasury += grant`, `last_growth_day = today` — только если компания ещё не росла сегодня **и** `grant ≤` текущий резерв;
  2. `server_reserve`: `balance −= grant` — только если компания реально была прокредитована (`last_growth_day = today`).

  Обе операции должны затронуть ровно по одной строке — иначе гонка/дефицит, изменений нет, повтор на следующем тике.
- **Если `grant = 0`** (резерв пуст или казна мала): `last_growth_day = today` фиксируется **без начисления** — компания пропускает день, без штрафов.

> Техническая деталь: интерактивные транзакции недоступны в `@libsql/client/web`, поэтому вместо них используется атомарный `db.batch` с условными `UPDATE`.

### 5.2. Роль резерва: источники и стоки

**Наполнение резерва:**

| Источник | Сумма |
|---|---|
| Создание компании | `cost − 500` (1-я: +500; 2-я: +30 500; 3-я: +60 500) |
| Покупка акций `/invest` | `reserveFee` ≈ 3% базовой стоимости |
| Продажа акций `/divest` | `reserveCut` = 5% выкупа |
| Ликвидация сезона | нераспределённые остатки казны компаний |

**Расход резерва:**

| Сток | Сумма |
|---|---|
| Суточный рост казны | до **100 🪙/день** на компанию |

**Если резерв пуст**: рост не начисляется (`grant = 0`), но день всё равно помечается пройденным — казна в этот день не растёт, цена стоит на месте. Резерв — единственный источник «пассивного дохода»: монеты не печатаются из воздуха, рост одних компаний финансируется комиссиями всей биржи.

### 5.3. Пример

Казна 5001, circulating 60 (состояние после сделок из §3.5). `desired = min(floor(5001 × 0.01), 100) = min(50, 100) = 50`. В резерве 1000 → `grant = 50`. Итог: казна **5051**, резерв **950**. NAV: 83.35 → **84.18** 🪙 — вот за счёт чего растёт котировка между сессиями торговли.

## 6. Кризисы компаний

### 6.1. Схема и жизненный цикл

В анализированных файлах кризисы представлены **схемой таблицы** `company_crises` и её очисткой при ликвидации сезона. Контракт по схеме:

| Поле | Смысл |
|---|---|
| `kind` | Тип кризиса (по умолчанию `'finance'` — финансовый) |
| `scenario_text` | Текст сценария, показанный игрокам |
| `player_reply` | Ответ игрока(ов) на кризис |
| `outcome_text` | Итог/разбор кризиса |
| `treasury_delta` | Изменение казны по итогам кризиса (может быть отрицательным) |
| `status` | Жизненный цикл; по умолчанию `'pending'` |
| `expires_at` | Дедлайн реакции на кризис |
| `channel_id`, `message_id` | Привязка к сообщению в канале (`message_id` UNIQUE) |

Индексы: `(status, expires_at)` — поиск просроченных кризисов; `(company_id, status)` — активные кризисы компании.

### 6.2. Влияние на казну и инвесторов

- `treasury_delta` применяется к казне → напрямую двигает NAV: отрицательная дельта обваливает цену, положительная — поднимает;
- Оценка портфеля (`/portfolio`) и выкуп (`/divest`) считаются от казны, поэтому кризис мгновенно отражается на капитале всех держателей;
- При ликвидации сезона все кризисы гильдии удаляются вместе с компаниями.

### 6.3. Границы анализа (проверено: worker.ts, db/queries.ts)

Логика **запуска** кризисов (когда и как они спавнятся) и их **разрешения** (обработка ответов, применение `treasury_delta`) **не найдена** ни в одном из переданных файлов:

- `worker/src/worker.ts` — маршрутизирует только `/company-create`, `/stocks`, `/portfolio`, `/invest`, `/divest`; обработчиков кризисов (команд/кнопок) нет;
- `worker/src/db/queries.ts` — общий слой запросов (пользователи, монеты, дуэли, инвентарь, рынок, квесты); хелперов для `company_crises` и биржи нет;
- `collector/src/collector.ts` — создаёт таблицу `company_crises` и её индексы, но в списке фоновых таймеров кризисов нет, функций спавна/разрешения тоже нет.

Вывод: кризисы существуют пока только как схема БД — рантайм-логика, судя по всему, ещё не реализована.

## 7. Конец сезона: ликвидация и дивиденды

### 7.1. Триггер и маркер сезона

- **Расписание**: проверка каждый час (+ при старте collector);
- **Сезон** определяется по месяцу (UTC): III–V `spring`, VI–VIII `summer`, IX–XI `autumn`, XII–II `winter`; ID сезона: `YYYY-spring` и т.п. → смена сезона раз в ~3 месяца;
- **Маркер** `last_season_reset` хранится **по гильдиям** в служебной записи `users` (`user_id = guild_id`) — как `last_week_reset` и `next_boss_spawn_at`;
- **Первый запуск** (маркер `NULL`): только инициализация маркера текущим сезоном **без ликвидации** — защита от того, чтобы деплой в середине сезона уничтожил компании вне границы сезона;
- Маркер обновляется **строго после успешного коммита** выплат: при сбое всё откатывается, и ликвидация повторится на следующем тике — компании не останутся брошенными без выплат;
- Ошибка в одной гильдии логируется и **не прерывает** обработку остальных; маркер ставится и гильдиям без компаний (их будущие компании корректно ликвидируются на следующей границе).

### 7.2. Формула дивидендов

Для каждой компании гильдии:

```
circulating  = 100 − available_shares
payout(h)    = floor(shares_count(h) × treasury / circulating)   // каждому держателю h
```

- Выплаты получают **все** держатели, включая владельца с его 51 акцией;
- Все начисления и очистка — **один атомарный `db.batch`** (ошибка любой записи откатывает всё);
- **Нераспределённый остаток** (потери на floor-округлении и казна компаний без держателей):

  ```
  remainder = treasury − Σ payout   →   server_reserve (balance += remainder)
  ```

- После выплат: `DELETE FROM company_crises / company_shares / companies` по гильдии; **`server_reserve` НЕ обнуляется** — баланс переходит в новый сезон.

### 7.3. Пример

Компания: `treasury = 10000`, `available_shares = 30` → `circulating = 70`.

- Владелец (51 акция): `floor(51 × 10000 / 70) = floor(7285.71) = 7285 🪙`;
- Инвестор (19 акций): `floor(19 × 10000 / 70) = floor(2714.29) = 2714 🪙`;
- Распределено: 9999; остаток `10000 − 9999 = 1 🪙` → в резерв сервера.

### 7.4. Что это значит для игроков

- Дивиденды пропорциональны пакету — к концу сезона выгодно держать акции компаний с «толстой» казной;
- После ликвидации биржа гильдии обнуляется: все компании исчезают, новые создаются снова по цене от 1000 🪙 (счётчик `count` стартует с нуля);
- Резерв сервера переживает сезон — накопленные комиссии продолжают «работать» в новом сезоне.

## Приложение А: шпаргалка формул

```
NAV            = treasury / circulating;   circulating = 100 − available_shares
Создание       cost = 1000 + count × 30000 (1-я: 1000);  резерв += cost − 500;  казна = 500
Покупка k      baseCost = ceil(k·T/C);  к оплате = ceil(1.06·baseCost)
               основателю floor(0.03·baseCost), резерву остаток
Продажа k      basePayout = floor(k·T/C);  на руки floor(0.95·basePayout);  резерву 5%
Суточный рост  grant = min(floor(0.01·T), 100, reserve);  T += grant;  reserve −= grant  (1 раз/сутки)
Дивиденды      payout = floor(shares × T / C);  остаток (T − Σpayout) → резерв
```

## Приложение Б: известные расхождения и TODO

1. **Инверсия правила 51 акции** (`/divest`, §4.3): условие `(shares_count - ? >= 51 OR ? = 0)` с параметром `isOwner ? 0 : 1` фактически ограничивает **не-владельцев** с пакетом 51+, а владелец может продать всё.
